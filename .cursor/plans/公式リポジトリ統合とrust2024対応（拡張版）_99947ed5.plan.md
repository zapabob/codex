### Phase 6: 公式リポジトリの最新機能取り込み

#### 6.1 upstream/mainの最新状態確認

**コマンド**:

```bash
git fetch upstream
git log upstream/main --oneline -20
```

**確認項目**:

- 最新コミットの確認
- セキュリティ修正の有無
- バグフィクスの有無
- 新機能の追加

#### 6.2 公式機能と独自機能の比較分析

**比較対象**:

- 公式の新機能 vs 独自機能（agents, plan, qc, orchestration）
- 公式のAPI変更 vs 独自機能の実装
- 公式のツール vs 独自ツール

**判断基準**:

- 公式機能が独自機能と同等以上の場合は公式を採用
- 独自機能が優れている場合は保持
- 両方の良い点を統合できる場合は統合

#### 6.3 upstream/mainのマージ

**手順**:

1. 現在のブランチをバックアップ
2. `git merge upstream/main`を実行
3. コンフリクト解決:

   - 公式の変更を優先（コア機能、バグフィクス、セキュリティ修正）
   - 独自機能は`#[cfg(feature = "custom-features")]`で保護
   - 両立可能な場合は統合

**保護対象**:

- `orchestration/`ディレクトリ
- `agents/`モジュール
- `plan/`モジュール
- `qc/`モジュール
- `cowork_integration`, `vr_ar_integration`, `llmops`など

#### 6.4 マージ後の検証

- ビルド確認: `cargo build --features custom-features`
- 型チェック: `cargo check --features custom-features`
- テスト実行: `cargo test --features custom-features`
- 独自機能の動作確認

## リスクと対策

### リスク1: upstream/mainのマージでコンフリクトが多発

**対策**:

- 段階的にマージ（小さなコミット単位）
- コンフリクト解決のドキュメント化
- 独自機能の条件付きコンパイルで保護

### リスク2: 独自機能のリファクタリングで動作不良

**対策**:

- 各修正後にテストを実行
- 段階的にリファクタリング
- バックアップの作成

### リスク3: スラッシュコマンドの実装が複雑

**対策**:

- 既存のスラッシュコマンド実装を参考
- 段階的に実装（1つずつ追加）
- テストの実装

### リスク4: アイコン作成が失敗

**対策**:

- 複数の変換方法を用意（ImageMagick、Python）
- デフォルトアイコンの使用を許可
- 手動でのアイコン作成も可能にする
